### ❌ 規格違反

- **[高] F-03 欄位級合併在「天」層級失效 → 資料遺失**
  - **位置**：`src/lib/merge.js:52-53`（`mergeDays`）
  - **PRD 要求**：§5.3「陣列以 id 為鍵做 union；同 id 比 updatedAt」；F-03 杜絕多人覆蓋。
  - **實際實作**：`mergeDays` 對同 id 的天用 `pick(cur, d)` 取**整個 day 物件**勝者，只有 `items` 另行合併。`city`/`lodging`/`date` 跟著整天勝者走。
  - **後果**：A 改某天 `city`、B 改同天 `lodging`，合併後只留 `updatedAt` 較新的一方，另一欄被**靜默丟棄**。等於把 v1「整份覆蓋」縮小到「整天覆蓋」，仍是 F-03 要消滅的 bug。T-04/T-05 實機兩裝置測試會失敗。
  - **建議修改**：把 `Day` 的 `city`/`lodging`/`date` 改為可合併純量 `{v,updatedAt}`，於 `mergeDays` 逐欄 `pick`；或保留扁平但加每欄時間戳逐欄合併。並補測試：同 day id，A 設 city、B 設 lodging，斷言兩者都在。

- **[高] F-05「不打斷輸入」未實作，編輯中欄位會被遠端覆蓋 → 資料遺失/UX 倒退**
  - **位置**：`src/hooks/useTrip.js:99-106`（realtime handler `apply(merged)`）＋ `DayCard.jsx:48,52` 等受控輸入。
  - **PRD 要求**：F-05/T-06，focus 中的欄位須延後套用遠端值。
  - **實際實作**：實作報告 §3 自承簡化為「每次按鍵蓋新 updatedAt，本地勝」。但受控輸入直接綁 `trip.data`，realtime 合併到來時 `apply(merged)` 會**替換輸入值**，造成游標跳動/掉字；若遠端該天較新（配合高-1）半打字的內容直接被蓋。「等價且更簡單」的說法不成立。
  - **建議修改**：用 `activeFieldRef` 記錄 focus 中的欄位/id，realtime handler 對該欄位延後套用（其餘照合併，本地值保留到 blur）；本地對逐鍵編輯做 debounce 再廣播。

- **[高] 離線→回線推送以過期 remoteRef 合併後盲蓋 → 覆蓋對方離線期間的寫入（資料遺失）**
  - **位置**：`src/hooks/useTrip.js:36`（`mergeTrip(dataRef, remoteRef)`）＋ `src/lib/sync.js:21-31`（`upsert` 無條件覆蓋整個 `data` 欄）。
  - **PRD 要求**：F-02/T-02→T-03→T-04 離線編輯回線後不可掉資料。
  - **實際實作**：離線期間收不到 realtime，`remoteRef` 停留在離線前；回線 `goOnline→doPush` 用**過期** `remoteRef` 合併後 `upsert` 整包，把對方在我離線期間 push 的內容蓋掉。
  - **建議修改**：`doPush` 改為 **read-merge-write**：先 `pullRemote(key)`→`mergeTrip(local, remote)`→再 upsert；並加樂觀鎖（比對 `updated_at`，衝突則重拉重併重試）。見中-5。

### ❌ 設計漂移
- **[中] 合併 tie-break 與契約不符、且非決定性**
  - **設計文件**：backend §5.2「同 updatedAt → 以 id 字典序決勝」。
  - **實際實作**：`src/lib/merge.js:17-23` 用 `JSON.stringify` 比大小。鍵序依建構路徑（migrate vs mutator）而異，可能跨客戶端不一致；tombstone vs 編輯同時間時勝負由字串隨機決定 → **跨端發散**（一端復活、一端維持刪除）。
  - **建議修改**：依文件用 `id` 字典序決勝，並讓 `_deleted` 在平手時固定勝出。補等時間戳收斂測試。

## 第三層：維護性審查

### ❌ 維護性缺陷
- **[中] `pending` 計數不準，推送成功即歸零，仍可能漏算佇列中的新編輯**
  - **位置**：`src/hooks/useTrip.js:43`（`setPending(0)`）vs `:58`（`+1`）。in-flight 推送期間的新 commit 會被成功 handler 歸零；且計的是 commit 次數非未同步項目數。「離線·N 筆」可能低報。
  - **建議**：以 IndexedDB `dirty` 旗標或「最後排入 seq vs 最後推送 seq」推導，僅當推送快照為最新 commit 時才歸零。

- **[中] 重試 timer 洩漏 + 可能並發推送迴圈**
  - **位置**：`src/hooks/useTrip.js:46-50, 109-118`。重試 `setTimeout(doPush)` 未存 handle；`online`/`retry`/`goOnline` 都直接呼叫 `doPush`，可能多個 `doPush` 並發（各自 stale-merge + upsert）。
  - **建議**：單航班化（`inFlight` ref 守衛）、保存並清除重試 timeout，effect cleanup 清掉所有 timer。與高-3 的 read-merge-write 一併修。

- **[中] debounce timer 未在 unmount 清除（`useTrip.js:57-61` 無 cleanup）。** 建議加 cleanup effect 清 `timer.current`。

- **[中] `pushRemote` 無樂觀鎖，盲蓋整個 data 欄（`sync.js:21-31`）。** 即使修好高-3，pull→upsert 視窗內兩端仍會整包 last-write-wins。建議條件更新（`.eq('updated_at', pulledTs)`）或把合併移到 Edge Function 做原子 read-merge-write。

- **[中] `validateTrip` 未檢查陣列項目 `id` 不變式（`schema.js:125-133`）。** 損壞項目通過驗證後，`mergeList`（`merge.js:36`）對 `id==null` 靜默丟棄 → 偽裝成通過的靜默資料遺失。建議驗證各 list 為陣列且每項有 string `id`，失敗則拒絕並走 F-07 提示。

### 低嚴重度
- **[低]** `addDays/addItem/addExpense` 的 `{ id: uid(), updatedAt: now(), ...item }` 把系統欄位放前面，caller 可覆蓋 id/updatedAt（`useTrip.js:129,151,176`）。建議 `{ ...item, id, updatedAt }`。
- **[低]** `api/flight.js:3` 預設模型 `claude-sonnet-4-6` 字串格式存疑；若 prod 未設 `FLIGHT_MODEL` 會每次 500（fail-soft 但功能形同停用）。建議用真實現役模型 id。
- **[低]** `mergeTrip` 僅白名單 key + `_v1backup`，未列舉的 top-level 欄位每次合併被丟（`merge.js:59-82`）。schema 新增欄位若忘了同步會在首次同步後消失。建議加守衛測試。
- **[低]** migrate 與 freshDefault 皆 `updatedAt:0`，新裝置開既有 v1 trip 時兩者平手，tie-break 非決定性可能顯示範例名而非真實名（`migrate.js:23`/`schema.js:13`）。修好決定性 tie-break + 既有 remote 時不混入 sample 即解。
- **[低]** 每次推送對整包 trip 跑兩次 `JSON.stringify`（validate + upsert，`schema.js:116-121`）。現規模可接受。

## 給技術總監的回饋

PRD 本身健全；但 **F-03 的資料模型在「天」這層留了破口**：`Day` 同時含 metadata（city/lodging）與 `items`，卻只把 `items` 設計成可合併。建議在 PRD §5.2 明確要求 day metadata 也走可合併純量，避免開發員把整天當單一 Mergeable。

## 驗收結論

**結論：不通過**

**理由**：3 個高嚴重度問題皆造成多人/離線情境下真實資料遺失（高-1 同天欄位、高-2 編輯被覆蓋、高-3 離線回線盲蓋），正是 v2 存在要消滅的 F-03/F-05 失效；單元測試全綠係因未涵蓋這些路徑而給出假信心。依團隊標準「任一高嚴重度 = 不通過」。

**後續行動（退回程式開發員修正）**：
1. **高-1**：`mergeDays` 對 day metadata 逐欄合併（city/lodging/date 改可合併純量）。
2. **高-2**：實作 `activeFieldRef`，realtime 合併時延後套用 focus 中欄位；逐鍵編輯 debounce。
3. **高-3 + 中-5**：`doPush` 改 read-merge-write（先 pull 再 merge 再 upsert）+ 樂觀鎖（比對 `updated_at`，衝突重試）。
4. **中-1**：tie-break 改 id 字典序、`_deleted` 平手勝出。
5. **中-2/3/4**：pending 計數、單航班化、timer cleanup。
6. 補測試：同天並發欄位編輯、離線回線合併、等時間戳收斂。
7. 修正後重新送驗收（第二輪）。
